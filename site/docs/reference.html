Command and tool reference

This page lists every cloudy-cloud command and flag, the six tools your session uses to run cloud agents, and the environment variables and files that change how they behave.

These commands and tools apply to every main session: Claude Code (cloudy-cloud), Codex (cloudy-cloud codex), opencode (cloudy-cloud opencode), pi (cloudy-cloud pi) and free-pi (cloudy-cloud free-pi). The cloud_agent profile argument picks the worker agent: Claude Code, pi, oh-my-pi, Codex or opencode. An opencode main session names the tools cloud_cloud_agent, cloud_cloud_agent_wait and so on.

Command line

These commands run on your computer. cloudy-cloud checks the first argument. If it is help, codex, opencode, pi, free-pi, dashboard, open, shell, display, coordinator, cloud, setup, --setup, doctor, protect, machines, branches or mcp-server, it runs that command. mcp ls, mcp add NAME, mcp add NAME --allow-literal, mcp rm NAME and bare mcp (which prints that command's usage) run cloudy-cloud mcp; any other mcp arguments go to Claude Code. Any other arguments start a Claude Code session. One bare word that is not a command and not a Claude Code subcommand (for example cloudy-cloud ls) is treated as a typo and fails with "is not a command", exit status 2.

cloudy-cloud (Claude Code as the main session)

cloudy-cloud [claude arguments]

The package installs the same command under two names, cloudy-cloud and cloudycloud; use either. Without a global install, npx cloudycloud runs the same command. Plain claude is not affected.

Starts a normal Claude Code session in the current folder. In that session the built-in Agent and Workflow tools are denied, and Claude starts subagents with the cloud tools described below. Run it from inside a git repository that has a github.com origin, because each cloud agent pushes its work to a branch there.

Every argument is passed to claude after the flags that cloudy-cloud adds itself (--mcp-config, --settings and --append-system-prompt). There are no cloudy-cloud flags of its own for a session.

Before it starts Claude, the command checks three things:

  • It needs an Instabox API key (from the environment or the config file) and a Claude token or Anthropic API key in the config file. If one is missing, it tells you. In a terminal it offers to run cloudy-cloud setup now. Outside a terminal it exits with status 1.
  • If the folder is not a git repository, it prints a warning that subagents cannot start.
  • If the repository has no github.com origin, it prints a warning that subagents cannot push their work.

Example:

cloudy-cloud --model opus

It also sets MCP_TOOL_TIMEOUT to 1800000 (30 minutes) unless you already set it.

cloudy-cloud codex, opencode, pi and free-pi

cloudy-cloud codex [codex arguments]
cloudy-cloud opencode [opencode arguments]
cloudy-cloud pi [pi arguments]
cloudy-cloud free-pi [free-pi-cli arguments]

Each command starts another coding agent as your main session, with the same cloud tools. Every argument after the subcommand goes to that agent. They are subcommands, not a flag, because Claude Code already has its own --agent option. None of them needs a Claude token to start, and setup does not ask for one unless you choose claude. They check only that the Instabox key (or the self-hosted settings) is saved, and run from inside a git repository with a github.com origin like cloudy-cloud. Workers run Claude Code unless cloud_agent gets a profile, so when no Claude token is saved, the command prints the profile to pass (for example codex) and tells the agent to pass it. To install an agent first, use the command in the third column.

cloudy-cloud --help and --version

cloudy-cloud --help
cloudy-cloud --version

--help (also -h or help, when it is the only argument) prints Cloudy Cloud's own commands, then points to claude --help for Claude Code's options. cloudy-cloud help <command> and cloudy-cloud <command> --help print one command's help without running it. The host commands are the exception: help codex (or opencode, pi, free-pi) prints a short note, while codex --help starts the host launcher and passes --help to the agent. --version prints the Cloudy Cloud version. With any other arguments, everything goes to Claude Code, for example cloudy-cloud -p "<prompt>" --allowedTools "Bash(git fetch *)"; see Run without the interactive UI.

cloudy-cloud setup

cloudy-cloud setup [--more] [--check-only] [--provider instabox|self-hosted|microsandbox]

Runs the bundled install.sh, whatever folder you are in. cloudy-cloud --setup does the same, and npx -y cloudycloud setup runs it without installing anything first (-y skips npm's "Ok to proceed?" question). Setup checks your tools, offers to install the cloudy-cloud command (npm install -g cloudycloud, or a link when you run it from a git clone), copies the Cloudy Cloud skills into ~/.claude/skills, uses the saved agent list or the agents it finds on your PATH (a fresh install picks claude alone when it is found; it asks which agents you run only when it finds none, and --more asks anyway), and asks for your Instabox key and your GitHub token, plus a Claude token only if you chose claude or want Claude workers and an OpenAI key for codex workers (--more offers it when codex is chosen or installed; plain setup offers it when codex is chosen and no saved credential could start a first worker — a saved Codex login file counts as one, even one a worker would later reject). Plain setup asks for the other model keys only in that same no-credential case; --more adds those steps and the cloud coordinators. Setup exits with status 1 when it ends without any worker credential. If an older cloudy-cloud global command blocks the install, setup offers to replace it (npm rm -g cloudy-cloud, then npm install -g cloudycloud). Run it again to change a key. It needs a terminal because it asks for keys. See Getting started.

FlagMeaning
--moreAdd the optional steps: cloud coordinators, Instabox usage alert emails and the other model keys (PARTICLE_API_KEY, OPENROUTER_API_KEY, OPENAI_API_KEY).
--provider instabox|self-hosted|microsandboxChoose where subagents run without being asked. self-hosted asks for your machine instead of an Instabox key. microsandbox is not configured by setup: it prints a pointer to the manual steps and exits. Any other value is refused. See Run on your own machine.
--check-onlyCheck the tools, the saved keys and the Instabox usage alert emails (on microsandbox: the msb binary, the worker image, the local keys and CLOUDY_CLOUD_EGRESS_ALLOW — an empty exported value with none saved in the env file is reported as unset, even though a worker rejects it), then exit. Does not need a terminal and changes nothing.

Example:

cloudy-cloud setup --check-only

cloudy-cloud doctor

cloudy-cloud doctor

Checks the machine that subagents run on when CLOUDY_CLOUD_PROVIDER is self-hosted: SSH, sleep settings on a Mac, the container runtime, disk, the worker image, slots, leftover containers and saved settings. Prints ok, warn or fail per check with a fix, and exits 1 if any check fails. With another provider it prints a one-line note. See Run on your own machine.

cloudy-cloud dashboard

cloudy-cloud dashboard [--demo] [--port N] [--no-open]
cloudy-cloud dashboard --prune

Starts a read-only web page on 127.0.0.1 that shows your cloud agents, coordinators and the messages between your session and them. It prints a link that contains a random token for this run, and opens it in your browser. Press Ctrl+C to stop it. See Dashboard and app previews.

FlagMeaning
--demoShow sample data instead of your machines. Nothing in it is real.
--port NListen on port N, from 0 to 65535. The default is 4477. If that port is in use, the dashboard uses a free port instead. Port 0 always picks a free port.
--no-openOnly print the link. Do not open a browser.
--pruneDelete every file under the streams folder (CLOUDY_CLOUD_STREAMS) that is older than 30 days, then the oldest until the folder is under 1 GB, and exit. Every file in that folder counts, not only stream files. The same pruning runs once when each agent's first turn starts.

Example:

cloudy-cloud dashboard --port 5000 --no-open

cloudy-cloud branches

cloudy-cloud branches prune [--yes] [--dry-run]

Run it inside your repository. It lists the cloudy-cloud/<8 hex characters> branches on origin (and cloudy-cloud/issue-<n>-<id> branches, for workers started from an issue) and compares each with origin's default branch. A branch that adds no commits to the default branch (it is empty, or already merged) is marked prune. A branch with commits not in the default branch is marked keep. It never touches a branch with another name.

It is a dry run: nothing is deleted unless you pass --yes. --dry-run forces a dry run even with --yes.

cloudy-cloud branches prune
cloudy-cloud branches prune --yes

cloudy-cloud open

cloudy-cloud open <agent-id-or-machine> <port> [--share]
cloudy-cloud open <agent-id-or-machine> <port> --unshare

Reaches an app, such as a dev server, that runs on a cloud agent's machine. The first argument is an agent id (the <id> in the branch cloudy-cloud/<id>, shown by cloud_agent_list), a machine name or a machine id (a coordinator's machine is named coord-NAME). It may use only letters, digits, dots, dashes and underscores. The machine must be running. The command needs your Instabox key.

With no flag, it opens a private tunnel from http://127.0.0.1:<port> on your computer to that port on the machine. It runs until you press Ctrl-C. Start the app in the background on the machine (for example nohup npm run dev > /tmp/dev.log 2>&1 &), because the foreground processes of a turn end with the turn. The tunnel and any shared link stop when the machine is deleted.

Argument or flagMeaning
<port>A port from 1 to 65535 on the machine. Write LOCAL:REMOTE to use a different port on your computer (not allowed with --share or --unshare).
--sharePublish a private link, with a token in the URL, instead of a tunnel. Anyone who has the link can open the app until the machine is deleted or you unshare it. It never publishes publicly.
--unshareRemove the link for that port. Cannot be combined with --share.

Example:

cloudy-cloud open 3f9a1c2e 5173

cloudy-cloud shell

cloudy-cloud shell <agent-id-or-machine> [-- command [args...]]

Opens an interactive login shell on a cloud machine. With -- command it runs that command, streams its output and exits with the command's exit code. Each argument after -- reaches the machine unchanged. Do not put secrets in the command. The first argument works as in open, and the machine must be running. Without a command it needs a terminal.

cloudy-cloud shell 3f9a1c2e -- uname -a

cloudy-cloud display

cloudy-cloud display <agent-id-or-machine> [--control] [--ttl SECONDS]
cloudy-cloud display <agent-id-or-machine> --screenshot FILE
cloudy-cloud display <agent-id-or-machine> --unshare

Prints a link to the desktop of a linux, android, gpu or macos machine (macos is not verified). Only the link goes to standard output. Anyone with the link can see the screen, so do not paste it into a PR, an issue or a report. An omarchy machine has no display. The first desktop start on a gpu machine takes about 2 minutes.

FlagMeaning
(none)A view-only link. It stops taking new viewers after 1 hour; a viewer already connected can stay.
--controlThe viewer can click and type.
--ttl SECONDSSeconds until the link stops taking new viewers, 60 to 86400. Not combined with --screenshot or --unshare.
--screenshot FILEWrite a PNG of the screen to a new file (an existing file or symlink is refused) and print the path.
--unshareRevoke every display link for the machine, including viewers already connected.

cloudy-cloud machines

cloudy-cloud machines [ls]
cloudy-cloud machines stop <id-or-name>
cloudy-cloud machines stop --all [--yes]

Lists the machines of the active provider that Cloudy Cloud made — machines labelled purpose=cloudy-cloud, or the older purpose=claude-cloud from before the rename — or deletes them. On microsandbox, listing also deletes expired microVMs as a side effect. In a terminal it prints a table with NAME, ROLE, STATE, AGE and DELETES; when piped it prints tab-separated NAME, ROLE, STATE, STARTED, DELETES and ID. It prints No Cloudy Cloud machines running. when there are none.

Argument or flagMeaning
lsList the machines (the default).
stop <id-or-name>Delete one machine at once, without asking. The token can be a machine id, an agent id, or a machine name; a name that matches more than one machine is refused.
stop --allDelete every machine in the list. It asks once on a terminal.
--yesSay yes to that question; needed to delete without a terminal.

cloudy-cloud protect

cloudy-cloud protect [owner/repo] [--yes]

Creates a GitHub ruleset named "cloudy-cloud: protect the default branch" on the default branch: changes need a pull request (zero approvals required), force pushes and branch deletion are refused, and the ruleset has no bypass actors — nobody it covers can push around it, including you and the cloud agents, which push as you. A repo admin can still edit or disable the ruleset in the repo settings. If an equivalent ruleset or classic branch protection already covers the branch, the command says so and changes nothing. It uses your own gh sign-in and you must be a repo admin. Without owner/repo it uses the repo of the current folder. It asks for confirmation first and changes nothing without a yes. On a private repo whose GitHub plan has no rulesets it explains the options (upgrade, make the repo public, or classic branch protection).

Argument or flagMeaning
owner/repoThe repo to protect. Default: the repo of the current folder.
--yesDo not ask first; you are saying yes to the change shown.

cloudy-cloud coordinator

cloudy-cloud coordinator image [--save]
cloudy-cloud coordinator start NAME --repo URL [--branch B] [--task TEXT | --task-file PATH] [--max-hours N] [--model NAME] [--env FILE]... [--json]
cloudy-cloud coordinator login NAME [--code CODE]
cloudy-cloud coordinator attach NAME
cloudy-cloud coordinator ls
cloudy-cloud coordinator status NAME [--json]
cloudy-cloud coordinator stop NAME
cloudy-cloud coordinator finish [--force]

Manages cloud coordinators: long-lived Claude Code sessions that run on their own Instabox machines and start workers there. All subcommands except finish need your Instabox key. With any other first argument, or none, the command prints this usage line. See Coordinators and fleets for when to use them.

coordinator image

Builds the machine image that coordinators start from. It is a one-time step. It creates an image machine (or reuses one you already started), installs cloudy-cloud on it, removes ~/.claude/.credentials.json on the machine — the image never holds a Claude sign-in, because each coordinator signs in for itself when it starts — then saves a snapshot, stores its id as CLOUDY_CLOUD_COORDINATOR_SNAPSHOT in the config file, and deletes the image machine. --save does the same wipe-and-save on an image machine that is still running. The server deletes an unsaved image machine after 2 hours. Only one image machine can exist at a time.

FlagMeaning
--saveSave the image machine as a snapshot and delete the machine.

coordinator start

Starts a coordinator named NAME on a new machine from the saved image. It sends this copy of cloudy-cloud (the checkout — a bundle of its committed state plus tracked uncommitted edits, leaving out files named like credentials, untracked files and staged additions — or the npm package's files), writes the coordinator's key file (mode 600), clones your repository to ~/repo, and starts Claude Code in a tmux session called claude through a launcher (~/.config/cloudy-cloud/launch.sh) that runs claude auth login while the coordinator is not signed in, then execs the session with Remote Control under the name NAME. A fresh coordinator waits at the sign-in until you finish it with coordinator login NAME — waiting for sign-in is a normal state and the machine is never deleted for it; on a terminal start attaches you to that pane so you sign in there. The coordinator never pauses. The server deletes its machine after --max-hours. Once signed in you can reach it from claude.ai/code or the Claude app (pick the session named NAME) or from a terminal with coordinator attach. The coordinator's Claude runs with permission checks off, like a worker, and the machine is set up so the bypass-mode confirmation and the folder-trust dialog never appear. If one still waits on a prompt, coordinator ls and coordinator status show it, and you attach and answer it. The first time, attach once and accept any Remote Control prompt.

Argument or flagDefaultMeaning
NAMErequiredLowercase letters, digits and -, up to 40 characters, starting with a letter or digit. A coordinator with the same name must not already exist.
--repo URLrequiredA https://github.com/OWNER/REPO URL.
--branch Bthe repository's default branchBranch to clone.
--task TEXTnoneA task for the coordinator to start on. Up to 100,000 bytes. Cannot be empty.
--task-file PATHnoneRead the task from a local file instead. Same limits.
--max-hours N24Hours until the server deletes the machine. At most 24, at least 60 seconds (1/60 hour). The deadline cannot be extended.
--model NAMEClaude Code's defaultModel for the coordinator's Claude Code session, such as opus or claude-opus-5-5. Rejected before any machine is created if it has characters other than letters, digits and ._:[]-.
--env FILEnone (repeatable)Bridge variables from a dotenv-style file to the machine; may be given several times. See Bridged env variables.
--jsonoffPrint one line of JSON with name, machine, remoteControlName, attach and started (true) instead of the usual text. A coordinator waiting for sign-in adds needsLogin, loginUrl (the claude.ai, claude.com or platform.claude.com URL the pane shows — never any other pane text) and next.

About 5 seconds after starting the session, the command reads its screen. If it shows a spend or usage limit or an invalid key, the command deletes the machine and fails with that line. If it waits on a trust, MCP approval or Remote Control prompt, the machine stays and the output (and waiting in --json) says to run coordinator attach NAME and accept it. A coordinator waiting at claude auth login is a normal state: the machine stays, the output says to run coordinator login NAME, and once you sign in (in the attached pane, or in your browser plus --code) the session starts. The session runs with --strict-mcp-config and has cloudy-cloud on PATH. If neither --task nor --task-file is given, the coordinator starts without a task. The command fails with a message if no coordinator image has been saved. A coordinator always runs Claude Code.

Example:

cloudy-cloud coordinator start docs-fleet --repo https://github.com/OWNER/REPO --task-file task.md --max-hours 8

cloudy-cloud cloud

cloudy-cloud cloud [--name N] [--branch B] [--max-hours H] [--model M] [--env FILE]... [--no-attach] [--json] is the one-command form of coordinator start plus coordinator attach: run inside a git clone whose origin is on github.com, it takes the repo from the origin URL, the branch from the checkout, and names the coordinator an <owner>-<repo>-<branch>-<hash> slug (--name overrides; the 7-character hash of owner/repo@branch always rides along so two different repos — or the same repo on two branches — can never collide, and a slug over 40 characters is truncated keeping the hash). If local <branch> has commits origin/<branch> does not (it is fetched first), or tracked files have uncommitted edits, it warns that the cloud clone comes from GitHub and will not have them — on a terminal it asks Start anyway? [y/N]; off one it refuses and names the push command. Untracked files only warn. It never pushes for you. An already-running coordinator of that name is reattached to (Reattaching to NAME) only when its machine is running and its install, repo and branch labels all match this checkout — a machine whose install label names a different cloudy-cloud installation, or that has no install label at all (made before coordinators carried one), is refused with the conflict named and --name or coordinator attach suggested. --env on a reattach does nothing (env files apply at start only) and says so. Otherwise it starts the coordinator exactly like coordinator start and, on a terminal, attaches; --no-attach, --json or a pipe prints the start output only, which includes the attach command.

Bridged env variables

coordinator start --env FILE and cloud --env FILE copy variables from a dotenv-style file to the machine (repeatable; the CLOUDY_CLOUD_ENV_FILES comma list in ~/.config/cloudy-cloud/env adds more). A variable whose name is already listed in your CLOUDY_CLOUD_PROXY_SECRETS is attached by name like any other custom proxy secret — the bridge never writes provider secrets. Any other variable needs per-repo consent (y for once, a remembered per origin in env-consent.json, which stores a SHA-256 of the value so a changed value asks again) and is then written NAME='value' into ~/.config/cloudy-cloud/env.local (mode 600, uploaded through the file route, never a command line) and sourced into the session's environment when tmux starts Claude. Names that could override the machine's own configuration or credentials (PATH, HOME, GIT_*, NODE_*, CLOUDY_CLOUD_*, CLAUDE_*, ANTHROPIC_*, XDG_*, INSTABOX_*, npm_config_*/NPM_CONFIG_*, PYTHON*, RUBY*, PERL5*, JAVA_TOOL_OPTIONS, _JAVA_OPTIONS, HTTP_PROXY/HTTPS_PROXY/ALL_PROXY/NO_PROXY in any case, CURL_*, SSL_CERT_*, REQUESTS_CA_BUNDLE, EDITOR, VISUAL, PAGER, BROWSER, TERM*, TMPDIR and the like) are always refused. On a provider without proxy secrets every variable needs consent. Variables cloudy-cloud already sends are always skipped. The summary names the proxied, copied and skipped variables with reasons, never values; a malformed line is reported by file and line number only, and an unterminated quote ends parsing there — nothing from that line onward is used; without a terminal unconsented variables are skipped.

A coordinator machine also runs a deadline watchdog in a detached tmux session cc-watchdog (script ~/watchdog.sh, log ~/watchdog.log), started with CLOUDY_CLOUD_COORDINATOR=1 and CLOUDY_CLOUD_DELETE_AT set to the deadline the provider reported for the machine. The deadline reminder reaches the Claude session through a Claude Code command hook (bin/deadline-hook.sh, wired for UserPromptSubmit and PostToolUse in the launcher's --settings): inside the last 30 minutes it emits additionalContext telling the session the delete time and to commit and push to a work branch — the watchdog never types into the session. Starting 5 minutes before deletion until the last minute the watchdog saves leftover work in ~/repo every poll: git add -u stages tracked edits only (untracked files are logged by name and count, never staged; files already added to the index are unstaged, logged by name and never committed — a staged credential file must not ride a WIP commit), a WIP: automatic save before the machine is deleted commit is made when needed (a failed commit is retried each poll and never pushed), then the current branch is pushed — done means a clean tree AND HEAD on origin/<branch> (fetched each poll; a failed fetch counts as unpushed). It never pushes to the push remote's default branch (a configured remote.origin.pushurl is asked with git ls-remote --symref <pushurl> HEAD; an unreadable remote means "protected"), to main, master or a release* branch, or while HEAD is detached — protected work goes to cloudy-cloud/wip-<timestamp> instead. It never force-pushes and never deletes anything; after a successful save it keeps polling and saves again only when something new appears, a push rejected at the branch destination is not retried there but lands on a fresh cloudy-cloud/wip-<timestamp>, and work still unsaved at the deadline exits non-zero. On the machine, the coordinator session may also use the built-in Agent tool for small tasks on its own machine; parallel or heavy work still goes to cloud_agent.

coordinator attach

Opens the coordinator's tmux session over SSH. On a terminal it opens the session itself. When the output is piped it prints cloudy-cloud coordinator attach NAME instead, and you run that in your own terminal. coordinator start and coordinator status show this same command, never the provider's own. It refuses a coordinator whose install label names a different cloudy-cloud installation; a coordinator with no install label (made before coordinators carried one) is still attached by name.

cloudy-cloud coordinator attach docs-fleet

coordinator login

Finishes a coordinator's Claude sign-in — each coordinator signs in for itself, and a fresh one waits at claude auth login until this runs. Without --code it attaches to the claude pane so you sign in there; a terminal is required (off one it prints an error pointing at --code), and when the pane shows Login expired or /login it prints Type /login and sign in. first. With --code — the way an agent finishes a sign-in the user did in a browser — it types the code (1–512 characters of letters, digits, #, _, -; anything else is rejected) into the pane's sign-in prompt, presses Enter, and waits up to 60 seconds for claude auth status to report the sign-in. It refuses --code when the pane is not showing the sign-in code prompt.

cloudy-cloud coordinator login docs-fleet
cloudy-cloud coordinator login docs-fleet --code OK-code_#9

coordinator ls

Lists your coordinators in a table with the columns NAME, STATE, STARTED (CREATED when the output is not a terminal), MACHINE and DELETES, plus a WAITING (SCREEN in a terminal) column when a screen needs a look. It reads each running coordinator's screen once: waiting for Claude sign-in means the pane waits at claude auth login (finish it with coordinator login NAME), waiting on a prompt: <line> means a prompt needs an answer, screen not read means the screen could not be read. It prints No coordinators. when there are none.

cloudy-cloud coordinator ls

When the output is piped, it prints tab-separated NAME, STATE, CREATED, MACHINE, DELETES and WAITING.

coordinator status

Read-only. Prints the coordinator's state, waiting for Claude sign-in when the pane waits at the sign-in (with the sign-in URL when the pane shows one), the prompt line it is waiting on (if any, with keys removed), the Remote Control link once Remote Control is connected (with a QR code on a terminal, to scan with a phone) and the attach command — or coordinator login NAME while it waits for sign-in. It reads the screen once. --json prints name, machine, state, screenRead, waiting, needsLogin, loginUrl, remoteControlUrl and attach (waiting, needsLogin, loginUrl and remoteControlUrl only when set; next names the finish-sign-in command while it waits). coordinator start prints the same link, and the QR code on a terminal, when Remote Control has connected by the end of the start wait; otherwise run coordinator status NAME later.

cloudy-cloud coordinator status NAME [--json]

Example:

cloudy-cloud coordinator status docs-fleet

coordinator stop

Deletes the coordinator's machine now. Its workers are deleted by the coordinator's cleanup process, or at their own deadline (6 hours by default). Anything the coordinator did not push to GitHub is lost.

cloudy-cloud coordinator stop docs-fleet

coordinator finish

Runs on the coordinator machine, started by the coordinator itself when its work is done. It checks that the working tree in ~/repo is clean, that the current branch and every fleet/* branch are pushed to their upstream, and that none of the coordinator's workers are still running. If all checks pass, it deletes its own machine. If a check fails, it lists the problems and deletes nothing. It refuses to run on a machine that is not a coordinator.

FlagMeaning
--forceSkip the git and worker checks and delete the machine anyway.

--force can delete work that has not been pushed. Use it only when you accept losing that work.

cloudy-cloud mcp

cloudy-cloud mcp add NAME [--allow-literal]
cloudy-cloud mcp ls
cloudy-cloud mcp rm NAME

Chooses which of your Claude Code MCP servers cloud subagents get. add copies one server from your Claude Code settings (local, project or user scope) to ~/.config/cloudy-cloud/mcp.json, replaces a secret value with ${MCP_<NAME>_TOKEN} and prints the npx --yes instabox@latest secrets set ... --host ... command that stores the value once in Instabox. ls lists the saved servers and the secrets they need. rm removes one. Only https servers on public hosts and npx or uvx servers are accepted; a refused server prints Not added: REASON and exits with status 1. --allow-literal asks you to confirm and then copies the real token to the machines — into the worker's own config file — instead of using an Instabox secret. All of this is described in MCP servers for subagents.

cloudy-cloud mcp-server

cloudy-cloud mcp-server

Runs the Cloudy Cloud MCP server on stdio, for MCP clients other than the built-in hosts. It prints nothing itself and runs before the setup check, so an empty config still answers tools/list. The server reads its keys from ~/.config/cloudy-cloud/env itself. Claude Code, Codex, opencode and pi sessions get the same tools through their own cloudy-cloud host command.

Tools the session uses (MCP)

cloudy-cloud adds an MCP server named cloud to the session. Claude sees its tools as mcp__cloud__cloud_agent and so on. The session is configured to allow these six tools without asking and to deny the built-in Agent and Workflow tools. You normally ask for subagents in plain language and Claude calls the tools. This section is for when you want to know exactly what each tool takes.

In a terminal Claude Code session that supports MCP tasks, cloud_agent and cloud_agent_message run as background tasks. Their progress shows in /tasks and the result arrives on its own with the agent id, so Claude does not need cloud_agent_wait. In other clients these two tools return an agent id at once and Claude calls cloud_agent_wait. The server also answers the task methods tasks/get and tasks/cancel.

cloud_agent

Starts a subagent in a remote sandbox on the committed and tracked files of the current repository. It does not include untracked files. The repository needs a github.com origin. The call returns at once while the sandbox starts and the task runs. The agent pushes its work to the origin branch cloudy-cloud/<id>. Nothing is copied into your local repository. The agent stays open for follow-ups until it is stopped or has been idle for 60 minutes.

Each turn is limited to 29 minutes by default. CLOUDY_CLOUD_TURN_MINUTES changes the limit (see Settings), and the prompt tells the agent when its turn ends. If a turn fails or hits the limit after the agent has started, the agent stays open with its session: call cloud_agent_message to continue it. A worker that commits nothing pushes no branch; the result says No changes, no branch pushed. and autofix does not start.

When ~/.config/cloudy-cloud/mcp.json holds at least one valid server, a Claude Code subagent (not a pi, omp, Codex or opencode worker) starts with --mcp-config for that file and --strict-mcp-config, so a repo's own .mcp.json is not loaded on the machine. pi, omp, Codex and opencode workers get the same servers in their own config files. The reply ends with an MCP servers: line. See MCP servers for subagents.

The call is refused if the session has already started CLOUDY_CLOUD_MAX_AGENTS_PER_SESSION agents (default 200), or if the folder is not a git repository with at least one commit and a github.com origin.

cloud_agent_message

Sends a follow-up message to an open agent that is idle, and continues the same conversation. It returns at once. As an MCP task the reply arrives on its own. Otherwise Claude calls cloud_agent_wait. It is rejected if the agent is busy or gone.

ParameterTypeRequiredDefaultMeaning
agent_idstringyesnoneThe id returned by cloud_agent.
messagestringyesnoneThe follow-up text.

cloud_agent_wait

Waits until every listed agent finishes its current turn, or until the timeout passes. For each agent it returns the status (starting, running, idle, failed or stopped) and its latest result. Each result is returned once. Later calls mark it as already reported. The tool is read-only.

ParameterTypeRequiredDefaultMeaning
agent_idsarray of stringsyesnoneThe agent ids to wait for.
timeout_secondsnumberno600How long to wait. Values above 1500 are limited to 1500.

cloud_agent_result

Returns an agent's latest result again, as often as asked, even after cloud_agent_wait or a task notification delivered it. If the agent has no result yet it says no result yet, status running. If the agent is not open it returns an error with a next step. The tool is read-only.

ParameterTypeRequiredMeaning
agent_idstringyesThe agent id.

cloud_agent_list

Lists every agent with its id, description, status, idle minutes and progress (tool uses, tokens, elapsed time and current step). The tool is read-only. With all: true it instead lists every machine on the provider labelled purpose=cloudy-cloud (other sessions and coordinators included), grouped by its parent label. Each worker machine carries the labels role, profile (claude for the default), parent, agent and a short redacted description.

cloud_agent_stop

Stops agents and deletes their sandboxes. It is safe to repeat, and safe to call with ids that do not exist. Stop agents when they are finished, because they stay open until stopped or idle for 60 minutes.

ParameterTypeRequiredDefaultMeaning
agent_idsarray of stringsyesnoneThe agent ids to stop.

Limits that apply to the tools

  • An agent that is idle for 60 minutes is stopped. Every agent is stopped when the session ends.
  • A single task is stopped after 29 minutes.
  • Machines start at most CLOUDY_CLOUD_STARTS_PER_MIN times a minute. Agents waiting for a machine show the status queued.
  • Instabox deletes every machine the tool creates after CLOUDY_CLOUD_WORKER_HOURS hours, even if cloudy-cloud has died.

Environment variables and files

Environment variables win over values in the config file. An empty value counts as unset.

Keys

VariableDefaultMeaning
INSTABOX_API_KEYnoneYour Instabox API key. Read from the environment or the config file.
CLAUDE_CODE_OAUTH_TOKENnoneThe long-lived token from claude setup-token. Cloud agents use it to sign in to Claude.
GH_TOKENnoneYour GitHub token. On a self-hosted machine it is read from the config file and placed in each worker container if you allowed that. See Run on your own machine.
ANTHROPIC_API_KEYnoneAn Anthropic API key, used by cloud agents when there is no Claude token. It is billed separately.
PARTICLE_API_KEY, OPENROUTER_API_KEY, and any other name ending in _API_KEYnoneProvider keys for model profiles. A profile's keyName must name one of these. A worker that uses a profile receives that profile's key.

The launcher only checks the config file for the Claude token, not the environment, so save it there with cloudy-cloud setup. The Instabox key can come from either place.

PathWhat it holds
~/.config/cloudy-cloud/envThe config file. One NAME=value per line, mode 600. cloudy-cloud setup writes it. Only the settings and keys listed above are read from it, plus CLOUDY_CLOUD_COORDINATOR_SNAPSHOT, which coordinator image --save writes. Change the location with CLOUDY_CLOUD_CONFIG.

~/.config/cloudy-cloud/mcp.jsonOptional. The MCP servers that cloud subagents get, in Claude Code's mcpServers format, mode 600. cloudy-cloud mcp add writes it. Secret values are stored as ${MCP_<NAME>_TOKEN} references unless you used --allow-literal. See MCP servers for subagents.
~/.config/cloudy-cloud/events.jsonlThe event log. The MCP server appends one JSON line per agent event (agent, message, machine, status, progress, reply). The file has mode 600 inside a folder with mode 700. It holds your prompts and replies, so it stays on your computer. Key-shaped text is redacted before writing, and each text is cut at 20,000 characters. It is never rotated: delete it to clear the history. The dashboard reads the newest 16 MB.
~/.config/cloudy-cloud/ownerAn id the MCP server writes next to the config file, so coordinator finish can tell which running machines are its workers. You do not need to edit it.

If you used the tool under its old name, claude-cloud, the first run copies ~/.config/claude-cloud to ~/.config/cloudy-cloud and renames the CLAUDE_CLOUD_ keys in the config file. The old folder is left in place.
